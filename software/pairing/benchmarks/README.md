# Benchmarks

The benchmark framework compares scalar DQMC output files against analytic, ED, or DQMC-reference JSON. The comparison entrypoint is:

```bash
python3 benchmarks/compare.py --reference benchmarks/references/triangle_pairing_fixture.json --run-dir benchmarks/fixtures/triangle_pairing_fixture_outputs
```

The Makefile exposes:

```bash
make check-fixtures
make benchmark-ed
make benchmark-fast
make benchmark-dqmc
make benchmark
```

`make benchmark-fast` and `make benchmark-dqmc` are currently backed by
committed live inputs and reference artifacts:

- `make benchmark-fast` runs the finite-\(\Delta\) DQMC-vs-ED smoke case in
  `runs/examples/triangle_pairing_ed_smoke` against
  `benchmarks/references/triangle_pairing_ed_smoke.json`.
- `make benchmark-dqmc` runs the suite in `benchmarks/dqmc_suite.json`, which
  includes the finite-\(\Delta\) smoke case and the `Delta=0` no-pairing
  regression in `runs/benchmarks/triangle_pairing_delta0_nopairing_3x2`.
- `make benchmark` aliases `make benchmark-dqmc`.

Treat these targets as the current committed regression suite, not as precision
physics production runs. The finite-\(\Delta\) case includes warm-up but remains
a moderate-size, loose-tolerance smoke test. The `Delta=0` no-pairing regression uses a committed
200-sample no-pairing reference, so its combined-error tolerance is currently
reference-error dominated. There is still no dual-repository live runner for
regenerating no-pairing output on demand, and no Makefile debug or bounds-check
target is currently defined.

## Benchmark A

Benchmark A is the `Delta=0` regression against the no-pairing triangular DQMC repository. Its purpose is to verify that the pairing code reduces to the corrected no-pairing normal-sector dynamics and observable semantics when anomalous pairing is disabled.

Current committed policy:

- pairing input has `RDelta = 0.0`;
- reference output is committed under
  `benchmarks/fixtures/nopairing_triangle_3x2_beta1_real_outputs`;
- paired observables use `reference_kind: "nopairing_dqmc_json"`;
- comparisons use combined block standard errors from the pairing and no-pairing samples.

The reference output was generated from the no-pairing repository commit
`a0c1b4414da7899f3ded4cc360201a5a34ff812c` and contains 200 samples. This is
enough for the current regression gate, but the combined-error tolerance is
reference-error dominated until a longer no-pairing reference is generated. The
committed `triangle_pairing_delta0_nopairing_fixture.json` remains a synthetic
parser fixture, not a real no-pairing physics reference.

## Benchmark B

Benchmark B is the finite-\(\Delta\) DQMC-vs-ED benchmark. Its purpose is to compare pairing observables against a full finite-temperature grand-canonical ED trace with controlled boson cutoffs. The committed `triangle_pairing_ed_smoke` case is a short smoke test with loose tolerances, intended to guard the pipeline and observable normalization rather than establish precision agreement.

Expected ED observables include `density_total`, `kinetic_total`,
`interaction_energy_total`, `interaction_energy_density`, `pairing_total`,
`pairing_energy_density`, `chemical_energy_total`,
`chemical_energy_density`, `energy_total`, `energy_density`,
`grand_energy_total`, `grand_energy_density`, `onsite_n2_up`,
`onsite_n2_do`, `S_SF_K`, `S_DW_K`, `S_PSF_Gamma`,
`same_flavor_pair`, and the compatibility keys `total_NE`,
`total_density`, `doubleOcc`, `local_numsquare`, `numsquare_up`,
`numsquare_do`, and `pair_equal`. `energy_density` is the physical/internal
energy density \(e=E/N_s\) excluding \(-\mu N\). Paper-facing reports should
plot the total-energy convention used in the no-pairing report,
\(-E=-N_s\,\texttt{energy\_density}\). Use `grand_energy_density` only as the
grand-canonical diagnostic. Do not compare `squareOcc` to ED unless an ED-side
density-product diagnostic is explicitly added.

## Pairing Delta Campaign

The repository keeps one default Delta-sweep manifest at
`benchmarks/campaigns/triangle_pairing_delta_3x3.json`. Dated research runs
should still live under ignored `data/` directories:

```bash
python3 benchmarks/campaign_pairing_delta.py write-manifest \
  --output data/20260605_pairing_delta_benchmark_pilot/manifest.json

python3 benchmarks/campaign_pairing_delta.py init-local \
  --manifest data/20260605_pairing_delta_benchmark_pilot/manifest.json \
  --output-dir data/20260605_pairing_delta_benchmark_pilot/inputs \
  --seed 24681357
```

The default manifest scans \(\Delta=0,0.1,0.2,0.3,0.4\) on a \(3\times3\)
triangular lattice with \(U_1=0\), \(U_2=1\), \(\beta=4\), and
\(\mu=-3.5\). For low-density pilots, write a dated manifest under `data/`
and override `--mu`, `--beta`, `--Nbin`, `--block-size`, `--nmax`, and
`--ncut` on the `write-manifest` command.

`paramC_sets.txt` generated by the campaign helper keeps the Fortran input
contract: the first non-empty, non-comment line is numeric and ordered as
`RU1 RU2 mu RDelta`; human-readable labels appear only after the seven fixed
numeric rows.

`benchmarks/pairing_delta_analysis.py` reads DQMC output fail-closed: missing
files, non-finite values, malformed complex rows, malformed
`density_site_total` rows, unequal sample counts, and incompatible \(K\)-point
geometries are rejected or marked unreliable. Complex observables use separate
real/imaginary block statistics; the real part is the comparison channel and
the imaginary part is a reliability diagnostic. The imaginary-part gate is
\(|{\rm Im}|\le \max(10^{-14},3\,{\rm SEM}_{\rm Im})\), so roundoff-scale
values are not rejected only because their block SEM is even smaller. With the
no-pairing triangular geometry convention, `sf_K` and `dw_K` are Hermitian
positive structure-factor channels; a failure of the imaginary gate, or a real
part negative beyond the same roundoff/block-error scale, marks the observable
unreliable. The \(\Gamma\)-point `psf_Gamma` uses the same imaginary-part
diagnostic.
The `IPR` derived from `density_site_total` is a DQMC spatial-uniformity
diagnostic. It is reported in summaries, but `ed_target_observables` does not
synthesize an ED pass/fail target from the ideal uniform value \(1/N_s\); at
very low density that nonlinear ratio is biased by finite-sample noise.

The committed `Delta=0` no-pairing regression is a smoke gate, not the full
publication observable audit against the no-pairing final campaign. Before a
paper-facing pairing report relies on inherited observables, check the current
no-pairing final repository definitions in addition to running the fixture.

## Reference Kinds

`benchmarks/compare.py` recognizes:

- `analytic`: expected values are embedded directly in the reference JSON.
- `ed_json`: expected values are read from a QuSpin ED result JSON through `expected_from`.
- `nopairing_dqmc_json`: pairing DQMC samples are compared with committed no-pairing DQMC samples.
- `live_nopairing_dqmc`: recognized but not implemented; use committed no-pairing output until a dual-repository live runner exists.

Supported DQMC operations include `mean`, `sum_mean`, `mean_times_nsite`, `mean_times_lq`, and `last`. The `mean_times_lq` name is an alias retained for compatibility; use `mean_times_nsite` for new references.

## Kinetic Naming Contract

```text
DQMC file `kinetic`: per spatial site.
ED JSON `kinetic_total`: total hopping expectation including the coefficient `t`.
DQMC-vs-ED and DQMC-vs-DQMC comparison operation: `mean_times_nsite`.
```

For this triangular pairing code, `Nsite=Lq` because `Norb=1`.

## `squareOcc` And `local_numsquare`

`squareOcc` is the no-pairing-compatible density-product diagnostic:

\[
\texttt{squareOcc}=
\frac{1}{N_s}\sum_i\mathrm{Re}\,[n_b(i,i)^2+n_c(i,i)^2].
\]

`local_numsquare` is the physical local number-square observable:

\[
\texttt{local_numsquare}=
\frac{1}{N_s}\sum_i\mathrm{Re}\,[D_{bb}(i,i)+D_{cc}(i,i)].
\]

Use the current `doubleOcc` for corrected no-pairing and ED comparisons. Use `squareOcc` only when comparing the corresponding density-product diagnostic.

## Block Statistics

When a DQMC spec contains `statistics.block_size`, `compare.py` converts each sample to the comparison scale, drops `skip_samples`, truncates to complete blocks, averages each block, and reports:

\[
\texttt{stderr}=
\frac{\mathrm{std}(\text{block means})}{\sqrt{N_{\mathrm{blocks}}}}.
\]

This is the standard error of the Monte Carlo mean estimated from block means, not the raw-sample standard deviation.

For one-sided comparisons,

\[
\texttt{tolerance}=
\max(\texttt{atol},\texttt{rtol}\,|\texttt{expected}|,
\texttt{stderr\_tolerance}\,\texttt{stderr}).
\]

For `nopairing_dqmc_json`, the combined-error rule is:

```text
actual = block_mean(pairing samples)
expected = block_mean(no-pairing samples)
stderr_combined = sqrt(stderr_pairing^2 + stderr_reference^2)
tolerance = max(atol, rtol * abs(expected), stderr_tolerance * stderr_combined)
pass if abs(actual - expected) <= tolerance
```

## QuSpin API Provenance

The ED scripts use official QuSpin APIs:

- `boson_basis_general` for the combined no-symmetry basis with `sps` and optional total `Nb` cutoff: https://quspin.github.io/QuSpin/generated/quspin.basis.boson_basis_general.html
- `tensor_basis` for the independent two-flavor cross-check: https://quspin.github.io/QuSpin/generated/quspin.basis.tensor_basis.html
- `hamiltonian` for operator construction and dense `H.eigh()` diagonalization: https://quspin.github.io/QuSpin/generated/quspin.operators.hamiltonian.html

Local Task 6 probes verified the same-site `"nn"` operator gives \(n_i^2\) for bosons and that the tensor-basis and combined-basis ED implementations agree on the tiny case. If future work adds a new QuSpin operator form, back it with an official documentation link or a small local probe recorded with the report.

## ED Caps

ED parameters are JSON files under `benchmarks/ed/`. Important fields:

- `nmax`: maximum occupation per boson mode.
- `ncut`: optional combined total-particle cap for `boson_basis_general`; use `null` for no combined cap.
- `basis_cap`: guardrail for dense diagonalization size.
- `--allow-large-basis`: manual override for intentionally large references.
- `--dense-memory-cap-gib`: guardrail for the estimated dense `H.eigh()`
  peak RSS in both the `boson_basis_general` and `tensor_basis` ED entrypoints.
  The default is 12 GiB; set a larger value only on an HPC node or other
  machine with explicit memory allocation. Set 0 only when deliberately
  disabling this guard.

The general `boson_basis_general` script estimates the constrained basis size
before constructing the QuSpin basis, then applies `basis_cap` and dense-memory
guards fail-closed.

The general script reports cutoff diagnostics: maximum total particles in the basis, total-cutoff boundary weight, and local `nmax` boundary weight. Treat large boundary weights as evidence that the ED reference is cutoff-sensitive.

### 3x3 ED resource policy

For the \(3\times3\) pairing benchmark, the combined ED basis has \(18\)
boson modes. The local WSL workstation has about 15 GiB RAM and 2 GiB swap;
do not run basis choices that require dense matrices near or above that scale.

Observed safe local checks:

- `nmax=2,ncut=4`: basis size 6973; used for the current dense ED references.
- `nmax=3,ncut=4`: basis size 7297; a local `mu=-4.0,Delta=0.4`
  dense check completed in about 1.5 minutes with peak RSS about 3.2 GiB.

Observed unsafe local checks:

- `nmax=2,ncut=5`: basis size 30229. The dense `H.eigh()` RSS estimate is
  about 54.5 GiB, so the default `--dense-memory-cap-gib 12` guard refuses it
  before dense matrix construction.
- `nmax=3,ncut=5`: basis size 33307. A single dense `complex128`
  matrix has size \(33307^2\times16\) bytes, about 16.5 GiB,
  before eigenvectors, LAPACK workspace, QuSpin data structures, and Python
  overhead; the calibrated dense `H.eigh()` RSS estimate is about 66.1 GiB.
  Do not run this cutoff on local WSL.
- `nmax=5,ncut=5`: basis size 33649. The calibrated dense `H.eigh()` RSS
  estimate is about 67.5 GiB. This is not a practical local WSL dense
  full-trace target; prefer lower-density benchmarks or a more efficient ED
  trace strategy before spending HPC queue time on this cutoff.
- Sparse low-energy checkpoints now evaluate observable diagonals with
  `operator.dot(evecs)` rather than dense `operator.toarray()`, so they are much
  safer for memory. They are still cutoff direction diagnostics only, not
  publication finite-temperature ED references, unless the report proves the
  truncated low-energy trace represents the full thermal trace.

Run `ncut=5` or larger \(3\times3\) dense full-trace ED only on HPC nodes with explicit
scheduler memory limits. For dense full-trace references, request at least
128 GiB RAM, pass a matching `--dense-memory-cap-gib` value, and record basis
size, wall time, peak memory, cutoff diagnostics, and whether the output is a
complete trace or a sparse low-energy checkpoint.
